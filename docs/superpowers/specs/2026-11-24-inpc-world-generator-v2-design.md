- 상태: 초안 v0.1 (2026-11-24). 빌더 검토 반영, 사용자 승인 대기.
- 근거: 바이옴 미리보기에 대한 사용자 의견과 결정. 원본은 [아이디어 노트](../../inpc/ideas.md)의 2026-11-24 항목이다.
- 상위 설계: [INPC 설계 v1.2](2026-11-23-inpc-design.md). 이 문서가 바꾸는 상위 설계 항목은 §7에 정리했다.

표시 규칙: 사용자가 정한 것은 표시 없이 적는다. 설계자(Claude)가 정한 것은 **[설계 결정]**, 빌더가 정할 것은 **[빌더 재량]**으로 표시한다.

## 1. 무엇을, 왜

G0.5에서 만든 바이옴 생성기(이하 1판)를 미리보기 그림으로 확인했고 세 가지 문제가 드러났다.

- 같은 바이옴이면 사진이 달라도 구성이 같고 색만 달라진다.
- 세계가 낮고 평평하다. 세계 높이는 12m, 언덕은 최대 2.5m, 지표 아래 땅은 2~4.5m뿐이다.
- 실내는 볼거리가 적어 게임 맵으로서 재미가 떨어진다.

2판의 목표는 사진마다 "그 사진 속 장소"처럼 느껴지는 세계다. 경치를 볼 수 있는 높이와 파고 내려갈 땅속도 있어야 한다.

성공의 기준은 상위 설계와 같다. 해 본 사람이 "자유도가 높다"고 느끼면 성공이다. 이번 단계의 확인 기준은 하나다. 같은 바이옴에 속하는 서로 다른 사진이 다른 장소로 느껴지는지 사용자가 미리보기와 게임 화면으로 판단한다.

## 2. 목표, 비목표, 실패 조건

**목표**

1. **장면별 구성.** 사진의 장면 종류에 따라 같은 바이옴 안에서도 지형과 구조물이 다르다.
   - 여행지 바다 사진: 해변. 해안가에서 바다 쪽으로 보이는 화면.
   - 동네 수영장 사진: 타일 바닥에 레일(레인을 구분하는 줄, 사다리 손잡이)이 있는 수영장.
2. **첫 화면 구도.** 출발점에서 처음 보는 화면이 사진의 구도를 닮는다. 바다 사진이면 해변에 서서 바다 쪽을 바라보며 시작한다.
3. **높이.** 세계가 높아지고 산, 절벽, 높은 곳이 있다.
4. **지하.** 땅을 파면 지하로 내려갈 수 있다. 지층, 동굴, 지하수, 땅속에 묻힌 것이 있다.
5. **실제 크기의 실내.** 실내는 "작아진 내가 거대한 방에 들어간 세계"가 아니라 집, 카페, 가게처럼 실제 세계에서 내가 있을 법한 공간이다.
6. **블록의 다양성.** 색만 바뀌는 것으로는 부족하다. 블록마다 재료 질감이 있고 금이 가거나 조금 손상된 블록 같은 변화가 있다.
7. **반복감 줄이기.** 맵마다 "본 적 있는" 비슷한 느낌이 반복되지 않는다.

**비목표 (2판에서 하지 않는 것)**

- 동물. 생물 단계(G4 무렵)에 따로 설계한다(사용자 결정 2026-11-24).
- 새 바이옴(습지, 정글, 남극·북극, 고원, 동굴 바이옴 등). 2판의 구조로 나중에 추가한다.
- 먼 산과 넓은 경치. 잃어버린 파일 맵이 붙어 세계가 확장될 때 해결한다(사용자).
- 사다리, 벽 타기 같은 새로운 이동 방법.
- 그림 파일로 그린 질감. 에셋 작업은 상위 설계 §6-6처럼 나중에 한다.
- 게임 안 부품 편집기.
- 보스와 이벤트(PC 사용자의 마우스 커서, 백신 프로그램 등). 방향만 아이디어 노트에 기록하고 나중 단계에서 설계한다(사용자 2026-11-24).

**실패 조건**

- 같은 장면 변형으로 만든 두 세계가 "본 적 있는" 느낌으로 반복된다.
- 블록 질감이 마인크래프트의 질감처럼 보인다(상위 설계 실패 조건 "마인크래프트 따라 했네").
- 높은 곳이나 방 대부분에 걸어서 갈 수 없다. 캐릭터가 갇힌다.
- 내장 그래픽(Iris Xe급) 1920×1080 중간 화질에서 평균 30fps가 나오지 않는다.
- 사진, 폴더·파일 이름이 PC 밖으로 나간다(상위 설계 §3).

## 3. 제약

- 상위 설계 §3을 모두 지킨다. Windows 먼저, Godot 4 .NET(C#), 사진은 PC 안에서만 읽기, 폴더 속 파일은 읽기만, 성능 하한.
- 블록 0.25m, 캐릭터 키 1.75m(블록 7개)는 그대로다.
- 파일 맵 한 장은 192×192칸을 유지한다. 먼 경치는 맵 확장으로 해결하기 때문이다. **[설계 결정]**
- 엔진과 무관한 로직은 Hangbar.Core에 두고 테스트한다.
- 같은 사진이면 같은 PC에서 같은 세계가 나온다(시드는 사진 내용).
- 개발 환경은 둘이다.
  - 리눅스 서버: Core 테스트, 서버 미리보기.
  - Windows PC: 게임 실행, 화면 확인, 성능 측정.

## 4. 접근 방식

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| (가) 장면별 규칙 추가 | 1판 생성기에 장면 변형마다 규칙 코드를 추가한다 | 가장 빠르다. 지금 코드를 그대로 확장한다 | 가구와 구조물을 코드로 하나씩 그려 실내가 투박하다. 같은 장면끼리 비슷해 보이기 쉽다 |
| **(나) 규칙 + 조립 부품 (채택)** | 지형과 큰 배치는 규칙으로, 집·방·가구·수영장 사다리·부두 같은 구조물은 미리 만든 블록 부품을 조합한다 | 실내가 실제 공간처럼 보이고 볼거리가 많다. 부품이 늘수록 세계가 다양해진다. 새 맵을 대부분 데이터 추가로 만든다 | 부품 제작 시간이 든다. 부품이 적으면 같은 모양이 반복된다 |
| (다) 사진 구도로 배치 | 사진을 거칠게 분할(예: 8×6칸)해 하늘·물·땅·덩어리의 위치를 세계 배치에 그대로 옮긴다 | "내 사진 그대로"라는 느낌이 가장 강하다 | G0에서 사진을 높이로 옮겼을 때 선이 벽이 된 문제와 비슷한 위험이 있다. 걷기 보장이 어렵고 맵 종류마다 옮기는 방법을 따로 정해야 한다 |

사용자는 (나)를 선택했다(2026-11-24). 확장성을 생각해도 (나)가 맞는지 함께 검토했다.

- 새 맵이 대부분 데이터 추가로 끝난다. 정글은 숲 규칙에 덩굴 부품을, 남극은 눈 지형 규칙에 얼음 부품을 추가하면 된다.
- 부품은 여러 맵에서 다시 사용한다. 압축 파일 던전, NPC의 집, 모바일 이식에도 같은 부품을 사용한다.

(다)는 가벼운 형태만 포함한다. 사진에서 수평선 높이와 주된 방향만 읽어 첫 화면 구도를 맞춘다(§6-8).

(나)를 선택하며 정한 조건은 세 가지다.

1. 부품은 데이터 파일로 저장한다. 새 맵을 코드 수정 없이 파일 추가로 만들기 위해서다.
2. 지형은 동굴을 파낼 수 있는 구조로 만든다.
3. 반복감은 색만으로 해결하지 않는다. 블록 재료 질감, 손상 상태, 부품 변형으로 해결한다(사용자).

## 5. 전체 흐름

```
 사진
  ├─ 인식 ──────────▶ 바이옴 + 장면 변형 (예: 물가 / 해변)
  ├─ 팔레트·분위기 ──▶ 색 역할에 칠할 색, 하늘·조명
  ├─ 수평선 높이 ────▶ 첫 화면 구도
  └─ 시드
        │
        ▼
 ① 지형 규칙 (높이, 절벽, 물, 길)          변형마다 다름
 ② 지하 (지층, 동굴, 지하수, 묻힐 자리)
 ③ 부품 배치 (구조물, 건물, 실내)          부품 파일 + 변형 매개변수
 ④ 블록 상태 (금 감, 이끼 낌, 닳음)
 ⑤ 큰 볼거리 1개 이상
 ⑥ 숨겨진 벽화, 출발점과 바라보는 방향
        │
        ▼
 블록 세계 (192 × 160 × 192칸) ──▶ 청크 메시 (재료·상태 포함) ──▶ 게임 화면
```

- ①~⑥의 순서와 단계 이름은 설계 결정이다. 각 단계 안의 규칙은 변형마다 다르다. **[설계 결정]**
- 1판의 결과물(`BiomeMap`)은 2판에서 구조물·부품·묻힐 자리·첫 화면 정보까지 포함하도록 확장한다. 형태는 빌더 재량이다.

## 6. 세부 설계

### 6-1. 장면 변형

바이옴 아래에 장면 변형을 둔다. 장면 변형은 "같은 바이옴 안에서 지형과 구조물이 다른 장소의 종류"다.

첫 세트는 바이옴마다 2~4개다. 해변과 수영장은 사용자가 정했고 나머지 목록은 설계 결정이다. **[설계 결정]**

| 바이옴 | 장면 변형 | 세계의 모습 |
|---|---|---|
| 들판 | 초원 | 완만한 언덕, 꽃, 바위 |
| 들판 | 농장 | 밭 이랑, 울타리, 헛간 |
| 도로 | 시골길 | 구불구불한 길, 가로수 |
| 도로 | 도심 대로 | 차선, 횡단보도, 인도, 신호등 |
| 도로 | 골목 | 좁은 길, 담장, 낮은 집 |
| 물가 | 해변 | 모래사장, 바다, 부두. 해안에서 바다 쪽을 바라보며 시작 |
| 물가 | 강·호수 | 물줄기, 다리, 강가 |
| 물가 | 수영장 | 타일 바닥, 레인 줄, 사다리 손잡이, 다이빙대 |
| 숲 | 숲 | 빽빽한 나무, 오솔길 |
| 숲 | 산 | 봉우리, 능선, 절벽, 등산로 |
| 숲 | 공원 | 잔디, 산책로, 벤치, 연못 |
| 도시 | 시내 | 고층 건물, 광장 |
| 도시 | 주택가 | 낮은 집, 마당, 골목 |
| 실내 | 집 | 거실, 부엌, 침실, 욕실 |
| 실내 | 카페·식당 | 카운터, 탁자, 의자 |
| 실내 | 가게 | 진열대, 계산대 |
| 실내 | 사무실·교실 | 책상 줄, 칠판·화면 |
| 교통 | 지하철역 | 승강장, 선로, 계단, 터널 |
| 교통 | 기차역·터미널 | 지상 승강장, 대합실, 지붕 |

- **인식.** Places365 장면 이름을 (바이옴, 장면 변형)으로 대응시키는 표를 사용한다. 지금의 `biome-labels.csv`에 변형 열을 추가한다. CLIP 후보는 장면 변형마다 문장 임베딩을 만든다. **[설계 결정]**
- **결과 형식.** `ThemeResult`와 `ThemeCache` 항목에 장면 변형을 추가한다. **[설계 결정]**
- **대체 규칙.** 색 어림짐작으로 바이옴만 정한 경우에는 그 바이옴의 기본 변형을 사용한다. 기본 변형은 초원, 시골길, 해변, 숲, 시내, 집, 지하철역이다. **[설계 결정]**
- **변형마다 정의할 것.**
  - 지형 규칙
  - 사용할 부품 목록
  - 첫 화면에서 바라볼 대상
  - 벽화를 숨길 수 있는 자리

### 6-2. 높이와 지형

- 세계 높이는 160블록(40m)으로 한다. 성능 측정 결과에 따라 128~192블록 범위에서 조정한다. **[설계 결정, 조정은 빌더 재량]**
- 기준 지표는 y=56 부근이다(지하 약 14m). 산은 지표 위 20m(y=136) 정도까지 오른다. 산 위로도 건축할 공간이 남는다. **[설계 결정]**
- 절벽을 허용한다. 1판의 "옆 칸 높이 차 2블록 이하" 규칙은 이제 길에만 적용한다. **[설계 결정]**
  - 산 정상과 고원에는 오르는 길(경사로, 계단, 오솔길)이 반드시 이어진다.
  - 건물은 들어갈 수 있는 건물(§6-4, §6-11)만 층과 옥상까지 계단이 이어진다.
  - 길의 칸은 옆 칸과 높이 차 2블록 이하, 머리 위 7블록 이상 빈 공간을 지킨다.
- 변형별 지형 예시
  - 산: 봉우리, 능선, 절벽, 등산로
  - 해변: 완만한 모래 경사와 넓은 바다
  - 공원: 완만한 언덕과 연못
  - 시내·실내·역: 평지 위에 구조물로 높이를 만든다
- 시험 기준
  - 출발점에서 걸어서 닿는 지표 칸이 맵의 70% 이상이다(1판과 같음).
  - 출발점은 막혀 있지 않다.
  - 높은 곳(가장 높은 지점이 속한 구역)에 길로 닿을 수 있다.

### 6-3. 지하

- **지층.** 위에서부터 표토(1~3블록), 흙, 돌, 깊은 돌 순서다. 깊이에 따라 다른 재료가 나온다. 색은 팔레트에서 정한다.
- **바닥.** 맨 아래 2블록은 부서지지 않는 바닥이다. **[설계 결정]**
- **동굴.** 지형을 만든 뒤 파내는 단계에서 동굴을 만든다. 일부 동굴은 입구가 지표로 열린다. 출발점 아래는 파내지 않는다. 동굴 벽은 벽화를 숨기는 자리가 될 수 있다(§6-8).
- **지하수.** 일부 동굴 바닥에 물이 고인다.
- **묻힐 자리.** 잃어버린 파일 조각(상위 설계 §6-3, G4)이 묻힐 위치를 결과물에 목록으로 남긴다. 2판은 위치만 만들고 묻히는 내용은 G4에서 정한다.
- **성능.** 1판 메셔는 막힌 땅속 면을 그리지 않는다. 따라서 지하의 그리기 부담은 동굴의 벽면에서만 발생한다.

### 6-4. 실제 크기의 실내

상위 설계 §6-3 바이옴 표의 실내 설명을 "작아진 내가 거대한 방에 들어간 세계"에서 "실제 세계에서 내가 있을 법한 공간"으로 바꾼다(사용자 결정 2026-11-24).

- **배치.** 맵 가운데에 건물을 두고 둘레에 하늘이 보이는 바깥(마당, 골목, 주차장 등)을 둔다. 건물은 1~2층과 옥상으로 구성되며 방 부품을 조합해 만든다. **[설계 결정]**
- **크기 기준.** **[설계 결정]**

  | 대상 | 실제 크기 | 블록 |
  |---|---|---|
  | 천장 높이 | 2.5~3m | 10~12 |
  | 문 | 폭 1m, 높이 2.25m | 4 × 9 |
  | 탁자 | 높이 0.75m | 3 |
  | 의자·침대 | 높이 0.5m | 2 |
  | 선반 | 높이 2m | 8 |
  | 벽 두께 | 0.25m | 1 |

- **가구와 물건.** 가구는 블록 부품이다. 컵, 화분, 전등 같은 작은 물건은 둥근 소품이다(상위 설계 §4-2).
- **창문과 문.** 창문은 투명한 유리 재료다. 문은 열린 출입구로 시작하고 열고 닫는 기능은 나중 단계에서 정한다.
- **출발점.** 실내 사진은 건물 안에서 시작한다(§6-8).
- **벽화.** §6-8의 숨김 규칙을 따른다. 건물 안에 숨기면 실제 크기의 액자다.
- **걷기.** 모든 방에 출발점에서 걸어서 닿는다(문, 계단).

### 6-5. 조립 부품

부품은 구조물을 구성하는 블록 집합이다. 부품 하나에는 다음 정보가 있다.

- 블록 배치와 각 블록의 재료
- **색 역할.** 블록 색을 고정하지 않고 "주색, 보조색, 강조색" 같은 역할로 저장한다. 세계의 팔레트가 역할마다 실제 색을 칠한다. 같은 부품도 사진마다 다른 색이 된다. **[설계 결정]**
- **연결점.** 문, 계단, 다른 부품과 이어지는 위치
- **변형 매개변수.** 길이 늘이기(벽 구간 등), 회전, 일부 빠짐(낡음), 손상 상태

큰 구조물(집, 부두, 승강장)은 작은 부품(벽 구간, 창문, 문, 계단, 기둥)을 조합해 만든다. 같은 조합이 반복되지 않게 하기 위해서다.

- 부품은 데이터 파일로 저장하고 Core가 읽는다. 읽기와 배치는 테스트한다. **[설계 결정]**
- 파일 형식은 빌더가 정한다. 처음 부품은 코드로 만들어 파일로 저장해도 된다. 나중에 블록 편집 도구에서 만든 파일을 불러올 수 있는 형식이면 더 좋다. **[빌더 재량]**
- 첫 세트는 장면 변형마다 구조물 3~6종이다. **[빌더 재량]**

### 6-6. 블록 재료, 상태, 질감

**블록 값.** 블록 하나에 색, 재료, 상태를 함께 저장한다. 1판의 16비트 값(색 15비트)으로는 부족하므로 32비트로 늘린다. 비트 배치는 빌더가 정하되 다음 조건을 지킨다. **[설계 결정, 비트 배치는 빌더 재량]**

- 색은 1판 이상의 정밀도를 유지한다.
- 재료는 16종 이상 표현한다.
- 상태는 4종 이상 표현한다.

**재료.** 첫 세트는 다음과 같다. 추가는 빌더 재량이다. **[설계 결정]**

- 땅: 흙, 풀, 모래, 돌, 깊은 돌, 바닥(부서지지 않음), 눈
- 구조물: 나무, 벽돌, 콘크리트, 타일, 금속, 유리(투명), 천

블록의 재료는 생김새(질감), 투명도, 부서지는지 여부를 정한다. 상위 설계 §6-4의 "제작 재료는 블록 색에서 나온다(사용자 확정 2026-11-23)"는 그대로 유지한다. 즉 블록을 캐서 얻는 제작 재료는 계속 색으로 정한다. **[설계 결정]**

**상태.** 멀쩡함, 금 감, 이끼 낌, 닳음 네 가지이고 여유 값을 남긴다. 생성할 때 규칙으로 배치한다.

- 오래된 구조물은 금이 간다.
- 그늘진 곳과 물가는 이끼가 낀다.
- 자주 다니는 길은 닳는다.
- 배치 규칙의 세부는 빌더 재량이다.

**질감.** 그림 파일 없이 셰이더(화면에 그릴 때 색을 계산하는 작은 프로그램)로 그린다.

- 면마다 8×8 픽셀 격자의 재료별 무늬다.
- 모티프는 사진이 깨질 때 보이는 8×8 압축 얼룩이다. "사진의 픽셀이 세계가 됐다"는 설정과 압축 찌꺼기 버그의 설정에 맞춘다.
- 같은 재료라도 블록 위치에 따라 무늬가 조금씩 다르다.
- 실패 조건: 마인크래프트의 질감과 닮아 보인다.
- 무늬의 세부 모양은 빌더 재량이다. 사용자가 미리보기와 게임 화면으로 최종 판단한다.

**메시.** Core의 청크 메셔는 정점마다 재료와 상태 정보를 함께 내보낸다. 게임의 셰이더는 그 정보로 질감을 그린다.

### 6-7. 반복감 줄이기

반복감은 네 층에서 줄인다.

| 층 | 방법 |
|---|---|
| 블록 | 재료 질감, 손상 상태 (§6-6) |
| 부품 | 크기·회전·빠짐·상태 변형, 작은 부품의 조합 (§6-5) |
| 장면 | 장면 변형마다 다른 지형 규칙과 부품 목록 (§6-1) |
| 세계 | 세계마다 그 세계에만 있는 큰 볼거리 1개 이상 (예: 바위 아치, 오래된 거목, 무너진 탑, 난파선, 분수) |

- 시험: 같은 장면 변형에서 시드만 다른 세계 두 개를 비교한다. 지형 높이가 다른 칸의 비율과 구조물 배치가 다른 비율이 기준값 이상이어야 한다. 기준값은 빌더 재량이다.
- 최종 판단은 사용자가 미리보기와 게임 화면으로 한다.

### 6-8. 첫 화면 구도와 숨겨진 벽화

- **수평선 높이.** 사진에서 하늘과 땅의 경계가 화면 높이의 어디쯤인지 대략 추정한다. 추정 방법은 빌더 재량이다. 추정에 실패하면 화면 가운데로 간주한다.
- **바라볼 대상.** 장면 변형마다 대상을 정한다(바다, 수영장, 건물 입구, 산봉우리 등). 출발점은 대상을 정면으로 바라보는 곳에 둔다. 처음 카메라 높이와 아래로 숙인 각도는 수평선 높이에 맞춘다.
- **안에서 시작하는 장소.** 실내 변형과 지하철역은 건물 안(지하철역은 땅속 승강장)에서 시작한다. 처음 화면에 하늘이 없더라도 사진 속 장소에 들어와 있는 느낌을 우선한다. 바깥으로 나가는 출입구나 계단을 출발점 가까이에 둔다. **[설계 결정]**
- **시야.** 출발점과 바라볼 대상 사이는 구조물과 소품이 시야를 가리지 않게 비운다. 1판의 "출발점에서 벽화까지 시야 확보" 규칙은 바라볼 대상 기준으로 바뀐다.
- **숨겨진 벽화(이스터에그).** 벽화는 출발점에서 보이지 않는 곳에 숨긴다. 영화의 이스터에그처럼 플레이 중 어디선가 발견하는 재미를 주기 위해서다(사용자 결정 2026-11-24).
  - 형태는 장소에 맞게 바꾼다(사용자 결정). 바깥과 동굴에서는 큰 그림판(최대 64×48블록, 16m×12m)이고 건물 안에서는 벽 한 면 크기의 실제 크기 액자다.
  - 숨기는 자리 예: 동굴 벽, 폭포 뒤, 산꼭대기 바위 면, 들어갈 수 있는 건물의 다락이나 지하실, 맵 구석의 숲속 공터. 장면 변형마다 후보 자리를 정한다.
  - 걸어서 또는 블록을 파서 닿을 수 있어야 하고 출발점에서 일정 거리 이상 떨어져 있어야 한다. 거리 기준은 빌더 재량이다.
  - 맵마다 1개다. 위치는 시드로 정하므로 같은 사진이면 같은 곳에 있다. **[설계 결정]**

### 6-9. 서버 미리보기 도구

- 리눅스 서버 임시 폴더에 있는 등각 미리보기(비스듬히 위에서 본 그림)를 저장소의 개발 도구 `tools/world-preview`로 옮긴다. 게임에는 포함하지 않는다. **[설계 결정]**
- 미리보기에 재료 질감과 손상 상태를 대략 표시한다. 실제 모습은 Windows 게임 화면으로 확인한다.

### 6-10. 맵 경계와 이웃 맵

상위 설계 §6-3에 따라 맵은 나중에 최대 3×3장이 붙는다. 2판은 맵 한 장을 만들지만 붙을 때 문제가 없도록 경계 규칙을 지금 둔다. **[설계 결정]**

- 맵 가장자리 16칸 안에서는 지형이 기준 지표 높이(y=56 부근)로 서서히 내려온다. 그래서 산 맵 옆에 수영장 맵이 붙어도 절벽이나 잘린 물이 생기지 않는다.
- 물은 가장자리에서 얕아지고 가장자리 칸에는 물을 두지 않는다. 해변의 바다도 가장자리 띠에서 얕은 물가로 끝난다.
- 생성기는 이웃 맵 정보를 입력으로 받지 않는다. 맵마다 시드와 팔레트가 다르므로, 같은 변형이 이웃해도 구성과 색이 다르다. 이웃끼리의 반복이 문제가 되면 G4에서 다시 다룬다.
- §6-7의 "세계마다 큰 볼거리 1개 이상"에서 세계는 맵 한 장을 뜻한다.
- 성능 측정(§8)은 맵 한 장 기준이다. 이웃 맵이 보일 때 멀리 있는 청크를 간단하게 그리는 방법(LOD)은 맵 확장 단계에서 정한다.

### 6-11. 실내 변형이 아닌 장소의 건물

시내 고층 건물, 주택가 집, 골목의 낮은 집, 농장 헛간, 역 대합실처럼 실내 변형이 아닌 장소에도 건물이 있다. **[설계 결정]**

- 대부분은 겉모양 건물이다. 속은 채워져 있고 문과 창문은 장식이다. 창문은 투명하지 않은 어두운 유리 재료로 그린다. 블록은 모두 파낼 수 있으므로 플레이어는 원하면 벽을 파고 들어갈 수 있다.
- 세계마다 1~2채는 들어갈 수 있는 건물로 만든다. 실내 변형의 방 부품을 사용하며 탐험할 곳을 만들기 위해서다.
- 이유: 모든 건물을 속이 빈 구조로 만들면 방·계단 부품이 몇 배로 늘고 그리는 면도 크게 늘어난다. 성능은 이 설계에서 가장 큰 위험이다(§8).

## 7. 지금 코드와 상위 설계에 주는 영향

**Hangbar.Core**

- 블록 값 16비트 → 32비트. `Block`, `VoxelWorld` 저장 방식, 관련 테스트
- 지형: 칸마다 높이 하나(`FileMap`)로 지표를 만든 뒤 블록 세계에서 파내는 단계 추가
- `BiomeGenerator`를 §5의 단계 구조로 재구성. 1판 규칙은 기본 변형의 출발점으로 다시 사용할 수 있다.
- `ChunkMesher`: 정점에 재료·상태 정보 추가
- 인식 결과: `ThemeResult`, `ThemeCache`, 라벨 표에 장면 변형 추가. CLIP 문장 임베딩은 변형 단위로 생성

**G0.5 계획.** 2판을 기준으로 남은 Task를 다시 계획한다.

- Task 4(모델 실행기): 장면 변형을 결과로 낸다.
- Task 6(게임 연결): 질감 셰이더, 높아진 세계, 유리 재료, 매끄러운 캐릭터(사용자 결정, 상위 설계 §6-5). 캐릭터는 생김새(머리·몸통·다리가 이어진 둥근 형태)만 바꾸고 지금 걷기 조작은 유지한다. 물리로 흔들리는 움직임은 상위 설계대로 G2(캐릭터 물리)에서 만든다. 좁은 실내에서 3인칭 카메라가 벽에 끼지 않는지도 Task 6에서 확인한다. **[설계 결정]**
- Task 7(두 후보 비교): 바이옴과 장면 변형의 정확도를 함께 비교한다. 통과 기준은 바이옴 80% 이상, 장면 변형 70% 이상이다. 시험 사진은 변형마다 2~3장, 모두 40~60장이다(사용자 결정 2026-11-24).

**1판 결정 중 바뀌는 것**

- 세계 높이 48블록 → 160블록
- 옆 칸 높이 차 2블록 제한: 지형 전체 → 길에만
- 벽화: 출발점 북쪽 30칸에서 보이는 48×36블록 → 숨겨진 이스터에그(바깥은 최대 64×48블록, 건물 안은 액자)
- 시야 확보 대상: 벽화 → 첫 화면에서 바라볼 대상
- 실내 설명

**상위 설계 v1.3에 함께 반영할 것 (진행 순서 ②, 설계 문서만 수정)**

- 실내 바이옴 설명(§6-3)
- 장면 변형, 높이, 지하, 블록 재료·상태(이 문서 요약)
- 음식: 배고픔 없음. 회복과 강화에 사용(§6-4)
- 쓰러짐: 도구·무기를 포함한 모든 소지품이 그 자리에 떨어지고 게임 시간 반나절 뒤 사라진다. 다시 일어나는 곳은 집(침대)이 있으면 집, 없으면 출발점(§6-4)
- 캐릭터: 머리·몸통·다리가 매끄럽게 이어진 이족보행, 물리로 흔들리는 띨띨한 움직임. 휴먼 폴 플랫은 분위기만 참고하고 생김새는 HANGBAR 캐릭터를 바탕으로 한다(§6-5)
- 동물: 방향만 기록한다. 생물 단계에서 따로 설계한다.
- 보스와 이벤트: 방향만 기록한다(마우스 커서, 백신 등). 백신을 플레이어 편 상인으로 둔 기존 아이디어(2026-11-23)와의 관계를 함께 정리해야 한다.

## 8. 시험으로 먼저 확인할 위험

- **성능(가장 위험).** 높이 160블록, 절벽, 동굴, 질감 셰이더를 합쳐도 내장 그래픽 평균 30fps를 지키는지 확인해야 한다.
  - 산 변형 + 동굴 + 질감 셰이더가 들어간 시험 장면을 먼저 만들어 Windows PC에서 `bench.ps1`로 측정한다.
  - 기준에 못 미치면 세계 높이 축소, 그림자 거리 축소, 같은 면 합치기 순서로 대응한다.
- **질감의 인상.** 마인크래프트처럼 보이지 않는지 사용자가 미리보기와 게임 화면으로 확인한다.
- **반복감.** 같은 장면 변형의 여러 시드를 미리보기로 비교해 사용자가 확인한다.

## 9. 진행 순서

2판을 두 단계로 분할해 만들고 첫 번째 결과를 사용자가 확인한 뒤 나머지를 진행한다. 질감과 반복감이 마음에 들지 않을 때 부품 전체를 다시 만드는 일을 막기 위해서다. **[설계 결정]**

| 단계 | 내용 | 끝났다고 보는 기준 |
|---|---|---|
| 2판-1 | 블록 32비트, 세계 높이, 지하, 질감 셰이더, 부품 파일, 서버 미리보기 도구. 장면 변형 4종(해변, 수영장, 집, 산) | 서버 미리보기와 Windows 게임 화면을 사용자가 확인한다. 성능 시험 장면 평균 30fps 이상 |
| G0.5 Task 4 | 모델 실행기. 장면 변형을 결과로 낸다 | 4종의 사진 12장(종류마다 3장)에서 장면 변형 70% 이상 |
| 2판-2 | 나머지 장면 변형 15종 | 변형별 미리보기를 사용자가 확인한다 |
| G0.5 Task 6·7 | 게임 연결, 사용자 사진으로 두 후보 비교 | 사진 40~60장에서 바이옴 80% 이상, 장면 변형 70% 이상. 그 밖의 기준은 G0.5 계획과 같다 |

## 10. 사용자 확인이 필요한 것

없음. 빌더 검토에서 나온 질문은 2026-11-24에 아래처럼 정했다.

- 실내와 지하철역 사진은 안에서 시작한다(§6-8). 설계자 판단이며 사용자가 이견이 있으면 바꾼다.
- 벽화는 숨겨진 이스터에그로 두고 형태는 장소에 맞게 바꾼다(사용자, §6-8).
- 장면 인식 통과 기준은 바이옴 80% 이상, 장면 변형 70% 이상이다(사용자, §7).
- 진행 순서(§9), 맵 경계(§6-10), 실내 변형이 아닌 장소의 건물(§6-11), Task 6의 캐릭터 범위(§7)는 설계자가 정했다.

**사용자가 할 일.** 시험 사진을 모은다. 2판-1 확인용 12장(해변, 수영장, 집, 산 각 3장)과 Task 7용 40~60장이다. 사진은 저장소 밖 Windows PC 폴더에 두고 여러 사람이 함께 사용하는 개발 서버에는 올리지 않는다(상위 설계 §3).
