# HANGBAR 설계

- 상태: v1.1 (2026-11-22 사용자 승인 v1.0 + 2026-11-23 M0 시험 결과 반영: `docs/spikes/2026-11-m0-results.md`)
- 작성일: 2026-11-22
- 제품 요구사항: [PRD.md](../../PRD.md) — 무엇을 왜 만드는지는 PRD가 기준이고, 이 문서는 어떻게 만드는지를 정한다.

표시 규칙: 사용자가 정한 것은 표시 없이 쓰고, 설계자가 정한 것은 **[설계 결정]**, 빌더가 정할 것은 **[빌더 재량]**으로 표시한다.

## 1. 목적 요약

가까운 친구(한 방 최대 8명)가 띨띨한 캐릭터가 되어 서로의 Windows 바탕화면 전체를 돌아다니고, 말풍선으로 대화하고, 공을 던지며 노는 앱을 만든다. 재미의 중심은 캐릭터의 움직임(슬랩스틱, 오르기, 맞고 넘어지기)이고, 메신저 기능은 그 재미를 거드는 정도로만 둔다. 다음 작품 HANGBAR: INPC(Steam 유료 게임)가 이 앱의 캐릭터와 코드를 이어받는다.

## 2. 목표, 비목표, 실패 조건

**원칙: 자유도**(사용자 결정 2026-11-22). 정해진 기능을 늘리기보다 모든 것에 똑같이 통하는 몇 가지 규칙(§6-9)을 두어, 사용자들이 스스로 놀이 방법을 만들어 낼 수 있게 한다. 단, 친구가 내 실제 PC(창, 파일)를 건드릴 수는 없다.

첫 출시라도 완성도를 갖춰 내놓는다(사용자 결정 2026-11-22). 캐릭터가 얼마나 활발하게 돌아다닐지는 사람마다 원하는 게 다르므로 사용자가 설정으로 정한다(§6-3 활동 설정).

**목표 (첫 출시)**
- 친구 캐릭터가 내 모든 모니터를 자동으로 돌아다니고, 모두의 화면에서 같은 사건(공 맞음, 넘어짐, 말풍선)이 실시간으로 일어난다.
- 작업표시줄, 바탕화면 폴더 아이콘, **열린 창의 위 가장자리**를 밟고 오른다. 창이 움직이거나 닫히면 그 위의 캐릭터는 떨어진다.
- 공 던지기, 말풍선 대화, 대화 기록.
- 내 캐릭터를 따라다니는 **펫**이 다른 방의 새 메시지를 알려 주고 그 방의 채팅 창을 열어 준다.
- 초대 링크 하나로 설치부터 친구 연결까지.
- 폴더를 입구로 한 WORLD. 서버에 저장되어 내가 꺼져 있어도 친구가 놀러 올 수 있다.

**비목표**: 파일 전송, 대화 검색, 읽음 표시, 공개 채널, 모르는 사람과 연결, 다른 메신저 확장, 깊은 탐험·건설(INPC 몫), Mac.

**실패 조건** (PRD §9): 일·게임 방해, 회사 보안 프로그램에 걸림, 폴더 이름 같은 개인정보 유출, 혼자면 할 게 없음, 반짝 유행.

## 3. 제약

- Windows 10/11 x64.
- 첫 출시 고정비 0원: Microsoft Store 배포(Store가 MSIX에 서명), Cloudflare Pages 무료, Supabase 무료 플랜.
- 로그인은 Google만.
- 다른 프로세스에 코드 주입, 전역 키보드·마우스 후킹(SetWindowsHookEx의 LL 훅 포함) 금지. 다른 메신저의 창·메모리를 읽지 않는다.
- 폴더 이름은 PC 밖으로 내보내지 않는다. 로그에도 남기지 않는다. 대화 내용도 로그에 남기지 않는다.
- 전체 화면 앱이 켜지면 자동으로 숨기고 그리기를 멈춘다.

## 4. 접근 방식

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **① Godot 4 (채택)** | 게임 엔진으로 클라이언트 전체를 만든다 | 물리·애니메이션 기본 제공, 투명 창·클릭 통과 내장, 가벼움, INPC와 엔진 공유 | 새 엔진 학습, 투명 창 위 한글 입력 검증 필요 |
| ② Electron + PixiJS | 웹 기술로 만든다 | TypeScript 그대로, 한글 입력·UI 쉬움 | 메모리 200MB+, 물리 별도, INPC로 이어지지 않음 |
| ③ Tauri + PixiJS | 웹 기술 + 가벼운 셸 | Electron보다 가벼움 | 투명 전체 화면 창·클릭 통과 사례 적음, Rust 학습 |

사용자가 ①을 골랐다(2026-11-22). 이유: 이 앱의 재미가 캐릭터 움직임에서 나오고, INPC를 같은 엔진으로 이어 갈 수 있다. Unity는 무겁고 요금 정책 변동 이력이 있어 후보에서 뺐다.

## 6. 클라이언트

### 6-1. 언어와 엔진

- **[설계 결정]** Godot 4 **.NET 버전, C#**을 쓴다. 이유: 바탕화면 아이콘 위치, 작업표시줄 위치, 전체 화면 감지 같은 Win32·Shell COM 호출이 핵심인데 C#은 P/Invoke와 COM interop으로 바로 부를 수 있다(GDScript는 직접 부를 수 없어 C++ GDExtension이 필요하다). 사용자의 Java 경험이 C#으로 쉽게 옮겨 가는 것도 이유다. Supabase와는 `HttpClient`로 직접 통신한다(M0에서 결정: 필요한 호출이 로그인·토큰 갱신 정도라 커뮤니티 클라이언트 supabase-csharp를 쓰지 않는다). 실시간 전송은 Supabase가 아니라 Cloudflare DO다(§7-3).
- 개발 환경(M0 확정): Godot 4.7.2 .NET, .NET 8 SDK. Godot .NET 내보내기는 프로젝트 폴더에 `<어셈블리 이름>.sln`이 있어야 한다.
- **[설계 결정]** 렌더러는 **Compatibility(OpenGL)** 로 시작한다. Windows에서 Forward+(Vulkan)의 픽셀 단위 투명은 GPU에 따라 문제가 보고되어 있다.
- **[빌더 재량]** Godot 4의 정확한 버전은 시험 제작(§11) 시점의 최신 안정판으로 고정한다.

### 6-2. 오버레이 창

- **프로세스는 모니터별 DPI 인식(PerMonitorV2)이어야 한다(M0 검토 C1).** 모든 Win32 좌표를 물리 픽셀로 다루기 때문이다. Godot 4.7.2는 스스로 "시스템 DPI 인식"만 요청하므로, 내보낸 exe에 PerMonitorV2 매니페스트를 넣는다(`packaging/dpi.manifest`, 리소스를 고쳐도 데이터가 깨지지 않게 pck는 별도 파일로 내보냄). 시작할 때 인식 모드를 기록하고 2가 아니면 경고한다. Godot 편집기에서 바로 실행하면 시스템 인식이라 배율이 섞인 모니터 시험은 내보낸 exe로 한다.
- 모니터마다 테두리 없는 투명 창을 하나씩 띄운다(픽셀 단위 투명, 항상 위, 작업표시줄 버튼 없음, 평소에는 포커스를 가져가지 않음).
- **[설계 결정] 창 크기는 모니터보다 1px 작게** 잡는다. 항상 위 창이 모니터 전체를 덮으면 Windows가 전체 화면 앱으로 오인해 작업표시줄을 내리거나 알림을 막고, 우리 앱의 전체 화면 감지(§6-3)가 자기 자신 때문에 "바쁨"을 돌려줄 수 있다. 시험 제작에서 확인한다.
- **[설계 결정] 클릭 통과는 커서 위치 조회 방식으로 한다.** 창은 기본적으로 클릭 통과 상태(`WINDOW_FLAG_MOUSE_PASSTHROUGH` / `WS_EX_TRANSPARENT`)이고, 앱이 `GetCursorPos`로 커서 위치를 조회해(커서가 캐릭터 가까이면 30ms대, 멀면 100ms대, 숨김이면 멈춤) 캐릭터·말풍선·공 위에 있을 때만 통과를 끈다. 전역 훅이 아니라 단순 조회라 보안 프로그램 문제가 없다. Godot의 `window_set_mouse_passthrough`는 쓰지 않는다: 다각형을 하나만 받고, Windows에서는 창 영역(SetWindowRgn) 방식이라 영역 밖이 그려지지도 않아 날아가는 공이나 래그돌이 잘린다. **M0 확인**: Godot의 `Window.MousePassthrough` 속성만으로는 다른 프로세스 창으로 클릭이 가지 않는다(`WindowFromPoint`가 여전히 우리 창을 돌려줌). 창을 만들 때 `WS_EX_LAYERED`(알파 255)를 붙이고 `WS_EX_TRANSPARENT`만 켜고 끄면 투명 그리기를 유지한 채 클릭이 뒤 창으로 간다.
- 내 캐릭터를 눌러 조종을 시작할 때만 그 창을 활성화해 키 입력을 받는다. 활성화가 거부되면(Windows 앞 창 잠금) 조종을 시작하지 않고 알린다. 조종이 끝나면(Esc, 다른 곳 클릭, 포커스 잃음) 원래대로 포커스를 가져가지 않는 상태로 돌아간다.
- **여러 모니터**: 캐릭터는 내 모든 모니터를 돌아다닌다(사용자 결정). 두 모니터가 맞닿은 경계에서는 걸어서 옆 모니터 창으로 넘어간다(한 창에서 사라지고 옆 창에서 나타남). 맞닿지 않은 경계, 높이가 다른 모니터의 빈 구간은 벽으로 취급한다. 모니터마다 DPI 배율이 다를 수 있으므로 시뮬레이션은 물리 픽셀 기준 가상 데스크톱 좌표 하나로 하고, 창마다 그릴 때만 변환한다.

### 6-3. 전체 화면 감지와 자원 사용

- 1초마다 두 가지로 판정해 하나라도 해당하면 모든 오버레이 창을 숨기고 그리기와 시뮬레이션 갱신을 멈춘다. 네트워크 연결은 유지하되 상태를 "바쁨"으로 바꾼다.
  1. `SHQueryUserNotificationState`가 `QUNS_BUSY`, `QUNS_RUNNING_D3D_FULL_SCREEN`, `QUNS_PRESENTATION_MODE`
  2. 앞 창(우리 창 제외)이 바탕화면·작업표시줄이 아니고, 자기 모니터 전체를 덮음. 요즘 게임이 많이 쓰는 테두리 없는 창 모드는 1번으로는 잡히지 않는다.
- 투명 오버레이가 떠 있기만 해도 게임·영상의 화면 출력 최적화(independent flip, MPO)가 꺼져 비용이 생길 수 있다. 그래서 숨길 때는 창을 투명하게 두지 않고 실제로 감춘다(hide).
- **[설계 결정]** 목표치: 보통 상태 30fps 상한, CPU 평균 2% 미만, 메모리 200MB 미만. 숨김 상태는 그리기 0, CPU 거의 0. **M0 실측(2026-11-23)**: CPU 1% 안팎·숨김 0.29%로 통과, 메모리 254~259MB(숨김 212MB)로 초과 — 메모리 목표는 사용자 결정 대기.
- "방해 금지"를 켜면 전체 화면과 같은 상태가 되고, 친구들에게 "바쁨"으로 보인다.
- **활동 설정**: 캐릭터 활동 정도(차분·보통·활발), 앞 창(지금 쓰는 창) 피하기 켬·끔, 화면 가운데까지 돌아다니기 켬·끔. 설정은 내 화면에만 적용되며 친구 화면에는 영향이 없다. 기본값은 **[빌더 재량]**.
- **빨리 숨기기 단축키**: 한 번 누르면 모든 캐릭터·펫·말풍선이 즉시 숨고, 다시 누르면 나타난다. `RegisterHotKey`로 등록한다(전역 훅 아님). 다른 앱이 이미 쓰는 조합이면 등록이 실패하므로 설정에서 바꿀 수 있게 하고 실패를 알린다. 기본 조합은 **[빌더 재량]**.

### 6-4. 바탕화면 지형

캐릭터가 밟고 오를 수 있는 것을 "지형"이라 부른다.

- **작업표시줄**: 주 모니터는 `SHAppBarMessage(ABM_GETTASKBARPOS)`, 보조 모니터는 `Shell_SecondaryTrayWnd` 창을 찾아 위치를 읽는다. 자동 숨김 작업표시줄이면 화면 아래 가장자리를 바닥으로 쓴다. 작업표시줄을 클릭하면 작업표시줄이 오버레이 위로 올라와 그 위의 캐릭터를 가릴 수 있다. 이는 받아들이고, 다음 조회 때 오버레이를 다시 맨 위로 올린다.
- **바탕화면 폴더 아이콘**: Shell COM으로 바탕화면 폴더 뷰(`IShellWindows.FindWindowSW(SWC_DESKTOP)` → `IFolderView`)를 얻어 각 항목의 위치(`GetItemPosition`)와 폴더 여부를 읽는다. 주의할 점:
  - `GetItemPosition`은 바탕화면 리스트뷰 기준 좌표라 화면 좌표로 바꿔야 한다(DPI 배율, 여러 모니터).
  - 항목 크기는 직접 주지 않으므로 `GetSpacing`과 아이콘 크기 설정으로 추정한다.
  - 아이콘을 옮겨도 셸 변경 알림은 오지 않으므로 2초마다 다시 읽는 것이 기본이다.
  - COM 호출은 전용 STA 스레드에서 한다.
  아이콘마다 위 면은 발판, 옆 면은 오르기 면이 된다.
- 폴더 이름은 **로컬 메모리에서만** WORLD 입구 별명 기본값 제안에 쓰고 저장·전송·로그에 남기지 않는다.
- 바탕화면 아이콘이 숨겨져 있거나 셸이 응답하지 않으면 작업표시줄과 화면 아래 가장자리만 지형으로 쓴다.
- "폴더 연결 끄기"를 켜면 Shell을 읽지 않고, 앱이 바탕화면 위에 직접 그린 폴더 건물만 지형으로 쓴다.
- **열린 창의 위 가장자리**(사용자 결정: 첫 출시에 포함):
  - 보이는 최상위 창을 `EnumWindows`로 Z 순서대로 훑고, 실제 테두리는 `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`로 얻는다. 최소화·숨김·클로킹(`DWMWA_CLOAKED`)된 창, 도구 창, 우리 창은 뺀다. **창 제목과 내용은 읽지 않는다.**
  - 각 창의 위 가장자리에서 더 위에 있는 창에 가려진 구간을 잘라 내고, 남은 구간만 발판으로 쓴다.
  - 캐릭터가 창 위에 있는 동안에는 그 창을 200ms마다, 나머지는 1초마다 다시 읽는다(**[빌더 재량]** 조정 가능). 창이 움직이면 위의 캐릭터도 함께 움직이고, 빠르게 움직이거나 닫히거나 최소화되면 캐릭터가 떨어진다.
  - "앞 창 피하기" 설정(§6-3)이 켜져 있으면 앞 창(사용자가 지금 쓰는 창)의 위 가장자리에 캐릭터가 오래 머물지 않는다.
- 지형은 "발판 선분 + 오르기 면"이라는 하나의 추상으로 다루고, 작업표시줄·아이콘·창·앱이 그린 폴더 건물이 모두 이 추상을 공급한다.

### 6-5. 캐릭터

- **첫 출시는 코드로 그리는 단순한 이족보행 캐릭터**(사용자 결정): 동그란 몸통과 머리, 막대 팔다리. 그림 파일 없이 Godot의 그리기 기능으로 부위별로 그린다.
- **부위별 구조**: 머리, 몸통, 위팔·아래팔, 허벅지·종아리를 각각의 부위 노드로 두고, 부위마다 "그리는 방법"을 갈아 끼울 수 있게 한다. 나중에 Claude Design, Higgsfield 등으로 만든 그림을 부위 단위로 바꿔 넣는다. 이 구조가 래그돌 마디와 그대로 대응한다. (AI로 만든 그림을 쓸 때는 해당 서비스의 상업적 이용 조건을 확인한다.)
- 동작 상태: 걷기, 서 있기, 앉기, 졸기, 오르기, 매달리기, 떨어지기, 넘어지기, 던지기, 맞기, 말하기.
- 넘어지기·맞기는 짧은 물리 기반 래그돌(몸통·머리·팔다리 몇 개 마디)로 우스꽝스럽게 만들고, 1~2초 뒤 일어나는 애니메이션으로 돌아온다. **[설계 결정]** 래그돌은 `RigidBody2D`와 조인트로 직접 만든다. Godot 4의 2D 물리 뼈대 수정자 계열은 불안정하다.
- 자동 돌아다니기: 각 캐릭터는 주인의 PC가 다음 행동을 정한다(§7-2). 행동 후보와 가중치는 **[빌더 재량]**이되 "일하는 사람 화면을 지나치게 가리지 않는다"를 지킨다. 화면 가운데에 오래 머물지 않고 주로 아래쪽·아이콘 주변에서 논다.
- 캐릭터를 잡아서 던질 수 있다(마우스로 집어 들기). 내 캐릭터는 조종할 수 있다(키 조작은 내 캐릭터를 클릭해 포커스를 받은 동안만, 전역 키 입력 없음).
- 다우메신저 시제품·Sure-Mate의 그림과 코드는 권리 확인 전까지 쓰지 않는다.

### 6-6. 말풍선과 채팅 창

- 메시지를 보내면 보낸 사람 캐릭터 머리 위에 말풍선이 뜬다(길이에 따라 3~8초, **[빌더 재량]**).
- 채팅 창은 작은 일반 창(투명 아님)으로 열고 닫는다. 대화 기록 보기와 입력을 맡는다. 투명 오버레이에서 입력기(IME)를 다루는 위험을 피하려고 **한글 입력은 이 일반 창에서만 받는다**.
- 트레이 아이콘: 채팅 열기, 방해 금지, 방 고르기, 설정, 종료.

### 6-7. 나의 WORLD

**구조**
- WORLD는 **구역**들로 이루어진다. 구역 하나가 폴더 하나에 대응하고, 구역마다 무작위 **씨앗 값**, 내가 붙인 별명, 내가 놓은 물건, 성장 정도가 있다.
- **[설계 결정] 씨앗은 폴더 이름의 해시가 아니라 무작위 값**이다. 이름의 해시를 쓰면 친구가 흔한 폴더 이름을 대입해 이름을 알아낼 수 있다.

**저장 (사용자 결정: 서버 저장 + 내 PC 사본)**
- 구역 데이터(씨앗, 별명, 물건, 성장 정도)는 **계정에 속하고 서버에 저장**한다. 내 PC에도 사본을 두어 로그인 전이나 연결이 끊겼을 때도 열린다. 로그인하면 서버와 맞추고, 충돌하면 나중에 바뀐 쪽을 쓴다.
- 회사 PC와 집 PC의 폴더는 다르므로 **폴더 연결(어느 폴더가 어느 구역의 입구인지)은 PC마다 로컬에만** 저장한다. 다른 PC에서 처음 로그인하면 기존 구역들은 앱이 그린 폴더 건물로 나타나고, 사용자가 원하면 그 PC의 폴더에 연결한다.
- 폴더 이름·경로는 서버에 가지 않는다.

**자라기**
- 바탕화면에 새 폴더가 생기면 새 구역이 생긴다(앱이 "새 구역 발견!"을 알린다). 연결된 폴더가 오래될수록, 그 구역에서 시간을 보낼수록 구역이 풍성해진다(나무가 자라고 장식이 늘어나는 식, 단계와 연출은 **[빌더 재량]**).
- 연결된 폴더가 지워지면 구역은 사라지지 않고 "연결 끊긴 구역"으로 남는다.

**들어가기와 함께 놀기**
- 캐릭터가 입구에 들어가는 동작으로 들어간다(마우스로 캐릭터를 입구에 놓거나, 조종 중 입구에서 위 방향키). 작은 별도 창에 그 구역 장면이 열린다. 업무 중에도 쓸 수 있게 창 크기를 작게 시작하고 바로 닫을 수 있다.
- WORLD 안은 장면이 모두에게 같으므로 바탕화면과 달리 위치까지 맞춘다(WORLD 객체의 세션, §7-4).
- **내가 꺼져 있어도 방 친구들이 내 WORLD에 놀러 올 수 있다.**
- **방문자 권한(사용자 결정)**: 방문자는 주인과 거의 같은 일을 한다. 옮기기, 부수기, 짓기, 물건 놓기, 방명록·선물 남기기가 모두 된다. 주인만 할 수 있는 일은 구역 별명 바꾸기, 폴더 연결, 자물쇠 걸기·풀기, 되돌리기다.
- **되돌리기(하루 1번 무료, 사용자 결정)**: 부순 일에 무게가 있어야 다툼과 예상 못 한 상황에서 재미가 생긴다. 그래서 되돌리기는 무제한이 아니다. 구역마다 "주인이 마지막으로 본 상태"를 스냅숏으로 남기고, 주인이 돌아오면 펫이 누가 다녀갔고 무엇이 바뀌었는지 알려 준다. 주인은 **하루 1번** 무료로 구역 하나를 그 스냅숏으로 되돌릴 수 있다(날짜 경계는 사용자 시간대 자정, 횟수는 WORLD 객체가 센다). 쓰지 않으면 부서진 조각을 모아 직접 다시 짓는다. 보관할 스냅숏 개수는 **[빌더 재량]**(최소 직전 1개).
- **자물쇠**: 물건이나 구역 일부에 자물쇠를 걸면 방문자가 옮기거나 부술 수 없다. 기본 자물쇠 1개는 무료이고, 더 많은 자물쇠와 디자인(금고, 보물상자, 함정)은 꾸미기 상품이다.
- **경비견**: 구역에 두면 방문자 캐릭터를 쫓아가 넘어뜨리는 펫이다. 꾸미기 상품이다. 넘어뜨리기는 §6-9의 일반 규칙(부딪힘, 넘어짐)으로 동작하므로 따로 기능을 만들지 않는다.
- 내 캐릭터가 WORLD에 들어가 있는 동안 바탕화면의 내 캐릭터는 입구 앞에서 기다리는 모습으로 남는다(친구들 화면에서도 같음).
- WORLD 안에서 할 수 있는 일은 돌아다니기, 함께 있기, 공 던지기, 물건 놓기(주인만), 방명록·선물까지다. 깊은 탐험과 건설은 INPC 몫이다.

### 6-8. 펫

- 사용자마다 자기 캐릭터를 따라다니는 펫이 하나씩 있다(코드로 그린 단순한 모양으로 시작, 나중에 꾸미기 상품).
- **방은 한 번에 하나만 켠다**: 여러 방의 구성원이어도 내 화면에 캐릭터가 돌아다니는 방은 지금 고른 하나다. 트레이나 펫 메뉴에서 바꾼다.
- 켜지 않은 방에 새 메시지가 오면 **펫이 "○○방에 새 메시지 3개!" 말풍선으로 알려 주고, 펫을 누르면 그 방의 채팅 창이 열린다**(사용자 결정). 채팅 창에서 그 방 사람들과 글로 대화할 수 있고, "이 방으로 가기"를 누르면 그 방을 켠다.
- 펫은 WORLD 방문 소식, 새 구역 발견 같은 알림도 전한다. 알림은 몰아서 하나로 보여 주고, 방해 금지·숨김 중에는 쌓아 두었다가 돌아왔을 때 한 번에 알린다.

### 6-9. 물건과 일반 규칙 (자유도)

§2의 자유도 원칙에 따라 모든 것에 같은 규칙을 적용한다.

- **모든 캐릭터·펫·물건은 같은 물리 규칙을 따른다**: 집기, 던지기, 쌓기, 부딪히기, 떨어지기. 공도 "가볍고 잘 튀는 물건" 하나로 다룬다.
- 물건은 속성 몇 개로 정의한다: 무게, 튀는 정도, 단단함(얼마나 세게 부딪히면 부서지는가), 집을 수 있는가, 위에 설 수 있는가. 새 물건은 속성 조합과 모양으로 추가한다.
- 부서진 물건은 조각이 되어 흩어지고, 조각도 같은 규칙을 따른다.
- 부딪힘이 충분히 세면 캐릭터는 넘어진다(래그돌). 공에 맞아 넘어지는 것, 경비견에게 넘어지는 것, 창이 닫혀 떨어지는 것도 모두 이 규칙으로 처리한다.
- **바탕화면에서도 같은 규칙**: 첫 출시에는 공을 포함해 바탕화면에 꺼내 놓을 수 있는 물건 몇 가지(종류는 **[빌더 재량]**)를 둔다. 바탕화면 물건은 사건(§7-2)으로 동기화되며, 던진 사람의 PC가 결과를 정한다.
- **실제 PC는 건드리지 않는다**: 캐릭터와 물건은 실제 창을 밟고 부딪힐 수는 있지만 창을 움직이거나 닫거나 클릭하지 않는다.

## 7. 동기화

### 7-1. 원칙

친구마다 해상도, 모니터 수, 아이콘 배치가 다르므로 **위치는 맞추지 않고 사건과 의도를 맞춘다.**

- 맞추는 것: 누가 접속했는가, 각자의 상태(보통·바쁨), 각 캐릭터의 현재 행동과 목표("아이콘 하나에 오르는 중", "화면 오른쪽으로 걷는 중"), 사건(던짐, 맞음, 넘어짐, 말풍선).
- 맞추지 않는 것: 픽셀 좌표, 지형.
- 각 PC는 받은 의도를 **자기 화면의 지형에 맞게** 실행한다. 예: "오르기 중"을 받으면 내 화면에서 그 캐릭터와 가까운 아이콘에 오른다.
- 대략의 가로 위치는 화면 폭에 대한 비율(0~1)로 보내 캐릭터 배치가 크게 어긋나지 않게 한다.

### 7-2. 권한

- **[설계 결정]** 각 캐릭터의 자동 행동은 **그 캐릭터 주인의 PC가 결정**하고 방송한다. 주인이 바쁨 상태면 졸기·앉기 같은 조용한 행동만 고른다.
- **[설계 결정]** 공 맞히기 판정은 **던진 사람의 PC가** 자기 화면 기준으로 한다. 결과("A가 B에게 던졌고 맞았다")를 방송하면 모두의 화면에서 공이 B에게 날아가 맞는 장면을 재생한다. 친구끼리 쓰는 앱이라 부정행위 방지는 목표가 아니며, 판정을 한 곳에서 하므로 서버가 필요 없다.
- **[설계 결정] 자동 돌아다니기는 씨앗으로 보낸다.** 주인 PC는 "행동 씨앗 + 시작 시각"을 몇 분에 한 번 보내고, 모든 PC가 같은 씨앗으로 같은 행동 순서를 각자 계산한다. 그 사이에는 사건(던짐, 맞음, 말풍선, 조종 시작·끝)만 보낸다. 늘 돌아다니는 캐릭터의 움직임을 매번 보내지 않으므로 메시지 양이 크게 준다. 조종 중일 때만 행동 변화를 바로바로 보낸다.
- 내가 내 캐릭터를 잡아 던지면 그 결과도 내 PC가 정한다. 남의 캐릭터를 잡아 던지는 것은 "B를 던졌다" 사건으로 방송하고, B의 PC가 받아들여 B의 행동을 그 사건으로 바꾼다.

### 7-3. 전송 수단

**[설계 결정] 실시간 전송은 처음부터 Cloudflare Durable Objects(DO)로 한다.** 직접 관리할 서버가 없고(사용자 우려: 서버 직접 관리), 무료 플랜에서 쓸 수 있으며(2025-04부터), "방 하나 = 객체 하나" 구조가 HANGBAR의 방과 맞는다. 처음 검토한 Supabase Realtime은 무료 동시 접속 한도가 낮고, 무료 VM(Oracle Cloud 등)은 사용량이 적으면 회수될 수 있어 뺐다.

- 앱 ↔ Cloudflare Worker ↔ DO를 WebSocket으로 잇는다. Worker는 접속할 때 Supabase가 발급한 토큰(JWT)을 검증하고, 그 사용자가 해당 방의 구성원인지 Supabase에서 확인한다(결과는 짧게 캐시).
- **방 객체**(`Room:<방 id>`): 접속자 목록(Presence), 상태(보통·바쁨), 캐릭터 꾸미기 정보, 행동 씨앗과 사건을 중계한다. 판정은 하지 않는다(§7-2). WebSocket Hibernation API를 써서 조용할 때는 사용 시간 요금이 붙지 않게 한다.
- 대화: 방 객체가 받아 즉시 중계하고, 기록용으로 Supabase `messages`에 쓴다.
- 연결이 끊기면 친구 캐릭터는 그 자리에서 졸다가 30초 뒤 사라진다. 다시 연결되면 다시 나타난다.
- **연결 유지(M0 검토 반영)**: 앱은 20초마다 맨 글자 `ping`을 보내고 방 객체는 런타임 자동 응답(`setWebSocketAutoResponse`)으로 `pong`을 돌려준다. 자동 응답은 방 객체를 깨우지 않으므로 조용한 방은 쉬는 상태로 남는다(2초 JSON ping이면 방 하나가 무료 사용 시간 한도를 거의 다 썼다). 답을 기다리는 ping은 하나뿐이고 왕복 시간은 앱이 직접 잰다. `ping`/`pong`은 예약어라 구성원이 보내도 중계하지 않는다.
- 앱은 연결 시도를 10초 안에 끝내지 못하면 포기하고, ping에 일정 시간(간격의 절반, 최소 6초) 넘게 답이 없으면 연결을 끊는다. 그 뒤 500ms부터 두 배씩 늘려 최대 30초 간격으로 다시 연결한다(M0에서 응답 없는 서버 앞에서 앱이 영원히 멈추는 결함을 찾아 정함).
- **토큰 만료**: 앱은 연결 직전 토큰 만료가 1분 안이면 refresh token으로 갱신한다. 서버가 401을 주거나 연결 중 만료로 4001로 닫으면 한 번 갱신해 다시 붙고, 그래도 거절되면 다시 로그인을 요청한다. 방 객체는 토큰 만료 시각을 소켓에 붙여 두고, 만료된 소켓이 보내는 메시지는 버리며 그 소켓으로는 더 이상 중계하지 않고 4001로 닫는다.
- 켜지 않은 방에는 접속하지 않는다. 새 메시지·방문 알림(펫)은 **사용자 객체**(`User:<사용자 id>`) 하나로 받는다.
- 시험 제작과 테스트에서 가짜 구현으로 바꿔 끼울 수 있도록 전송 계층은 앱 안에서 인터페이스(방 입장·퇴장, Presence, 사건 보내기·받기) 뒤에 둔다.

### 7-4. WORLD 세션

- **WORLD 객체**(`World:<주인 id>`): 그 사람의 WORLD 구역, 물건, 방명록, 되돌리기 스냅숏을 DO의 SQLite 저장소에 보관하는 원본 저장소이자, 방문자들의 위치를 맞추는 세션이다. 주인이 꺼져 있어도 동작한다.
- WORLD 안은 장면이 모두에게 같으므로 위치까지 맞춘다. 물건의 물리는 그 구역에 가장 먼저 들어온 사람의 PC가 계산해 방송하고(그 사람이 나가면 다음 사람에게 넘김), WORLD 객체는 확정된 결과(물건 위치·부서짐)를 저장한다. 방문자 수가 적고 친구끼리라 이 정도로 충분하다.
- 같은 방 구성원만 들어올 수 있다. 자물쇠 걸린 물건의 변경은 WORLD 객체가 거절한다.
- 앱의 내 PC 사본(§6-7)은 로그인 후 WORLD 객체와 맞춘다.

## 8. 서버 (Supabase)

### 8-1. 로그인

- Google OAuth, PKCE 흐름. 앱이 기본 브라우저로 Supabase 로그인 주소를 열고, 로그인이 끝나면 **루프백 주소(`http://127.0.0.1:<포트>/callback`)로 돌아오게 해 앱 안의 작은 HTTP 수신기가 코드를 받는다.** 데스크톱 앱용으로 Google이 권장하는 방식이다. 포트는 53682 → 53683 → 53684 순으로 시도한다(M0 확정, Supabase 리디렉트 허용 목록에 셋 다 등록). 수신기는 `HttpListener`가 아니라 127.0.0.1 TCP 수신기다(`HttpListener`는 127.0.0.1에 관리자 권한의 URL 예약이 필요할 수 있다).
- 세션 토큰은 Windows 자격 증명 관리자(Credential Manager) 또는 DPAPI로 암호화해 저장한다.

### 8-2. 데이터

```
profiles      id(=auth uid), display_name, avatar(jsonb: 꾸미기), created_at
rooms         id, name, owner_id, max_members(기본 8), created_at
room_members  room_id, user_id, joined_at        -- PK(room_id, user_id)
invites       code, room_id, created_by, expires_at, max_uses, uses
messages      id, room_id, user_id, body(최대 500자), created_at
pets          user_id, look(jsonb)
```

- WORLD 데이터(구역, 물건, 방명록, 스냅숏)는 Supabase가 아니라 WORLD 객체(§7-4)에 있다. Supabase에는 계정, 방, 구성원, 초대, 대화만 둔다.

- 모든 테이블에 행 수준 보안(RLS): 방 구성원만 그 방의 `rooms`, `room_members`, `messages`를 읽는다. 쓰기는 본인 행만.
- **방 최대 8명은 서버에서 강제한다.** 초대 수락은 `accept_invite(code)` DB 함수 하나로만 하고, 함수 안에서 인원·만료·사용 횟수를 잠금과 함께 확인한다. 9명 이상 확장(유료)은 `max_members`를 올리는 방식으로 나중에 붙인다.
- **[설계 결정]** 대화 기록은 30일 보관 후 삭제한다(예약 작업). 이유: 무료 플랜 저장 용량을 지키고 개인정보처리방침에 적기 쉽다. 사용자가 다르게 원하면 바꾼다.
- 폴더 이름, 폴더 경로, 씨앗 대응표는 서버에 없다.
- **[설계 결정] 첫 출시에 넣는 계정·방 관리**: 방 나가기, 방장이 구성원 내보내기, 방장이 나가면 가장 오래된 구성원에게 방장 넘기기(마지막 사람이 나가면 방 삭제), 계정 삭제(프로필·구성원 기록·대화를 함께 지움). 계정 삭제는 개인정보 보호법상 필요하다.
- **[설계 결정] 신고·차단**: 친구를 차단하면 그 사람의 캐릭터와 말풍선이 내 화면에 보이지 않는다. 신고는 웹사이트의 신고 양식(메일)으로 받는다. Microsoft Store는 사용자 콘텐츠(채팅)가 있는 앱에 신고 수단을 요구할 가능성이 있다(정확한 조항은 Store 제출 전에 확인).

### 8-3. 무료 플랜 유의점

- Supabase 무료 프로젝트는 일정 기간 활동이 없으면 일시 중지된다. 출시 후에는 사용자가 있으니 문제가 적지만, 개발 중에는 재개하는 절차를 알아 둔다.
- Cloudflare DO 무료 한도(2026-11 확인): 하루 요청 10만 건, 사용 시간 하루 13,000GB-s, 저장 5GB. 받는 WebSocket 메시지는 20건을 1건으로 세고 보내는 메시지는 세지 않는다. 한도를 넘으면 그 종류의 요청이 실패하므로, 하루 사용량이 한도의 70%에 이르면 유료 플랜(월 $5부터)으로 넓힌다. 공개 출시 전 부하 시험에서 사용자당 하루 요청 수를 실측한다.

## 9. 웹사이트 (Cloudflare Pages, 정적)

- 페이지: 소개(`/`), 다운로드(`/download` → Microsoft Store 링크), 초대(`/i/<코드>`), 이용약관, 개인정보처리방침.
- 초대 페이지는 정적 HTML 하나와 `_redirects`로 `/i/*`를 받는다. 페이지의 스크립트가 기기를 보고 갈린다.
  - 휴대폰: "PC에서 이 링크를 열어 주세요" + 링크 복사 + 카카오톡으로 나에게 보내기.
  - PC: **"HANGBAR에서 열기"(`hangbar://join/<코드>`)와 "설치하기"(Microsoft Store) 버튼을 함께** 보여 준다. 브라우저는 앱 설치 여부를 알려 주지 않으므로 자동 판단하지 않는다. 설치 후 첫 실행에서 코드를 이어받는 방법은 **[빌더 재량]**(예: 사용자가 페이지의 "코드 복사"를 누르면 앱이 첫 실행에서 클립보드의 HANGBAR 코드를 제안).
- 카카오톡 공유는 웹사이트에 Kakao JavaScript SDK를 붙여 한다(Kakao Developers 앱 등록, 무료). 앱의 "카카오톡으로 초대" 버튼은 이 페이지를 연다.
- 사이트 생성 도구는 **[빌더 재량]**(정적 HTML, Astro 등). 회원 기능 없음.

## 10. 배포

- Godot .NET 내보내기 결과를 **MSIX로 포장**해 Microsoft Store에 낸다. Store가 인증 후 서명한다.
- MSIX 매니페스트: 전체 신뢰(`runFullTrust`), `hangbar://` 프로토콜 등록, 시작 프로그램 등록(사용자가 끌 수 있게, 기본 켬은 **[빌더 재량]**).
- 자동 업데이트는 Store가 한다.
- Store를 막은 회사 PC를 위한 직접 배포(코드 서명 인증서 필요)와 Steam은 첫 출시 범위 밖이다.

## 11. 시험 제작 (먼저 확인할 위험)

본 개발 전에 아래를 작은 시험 프로그램으로 확인하고 결과를 기록한다. 하나라도 안 되면 이 설계로 돌아와 대안을 정한다.

1. Godot 4 .NET(Compatibility 렌더러)으로 **모니터마다 투명·항상 위 창**을 띄우고:
   - 커서 조회 방식의 클릭 통과 전환이 동작하는지
   - 1px 작은 창이 Windows에 전체 화면으로 오인되지 않는지(작업표시줄, 알림, 우리 자신의 전체 화면 감지)
   - 전체 화면 게임과 테두리 없는 창 모드 게임 양쪽에서 숨김이 되는지
   - 모니터 두 개일 때 창마다 드는 렌더링 비용
2. **바탕화면 아이콘 위치를 C#에서 Shell COM으로** 읽을 수 있는지. 회사 PC 보안 프로그램(가능하면 실제 회사 PC)이 막거나 경고하는지.
3. **한글 입력**: 채팅용 일반 창에서 한글 조합이 정상인지.
4. **두 PC 동기화**: Cloudflare DO(WebSocket)로 행동 씨앗·사건을 주고받을 때 체감 지연(목표 200ms 안팎), Godot C#에서 WebSocket과 Supabase 토큰 검증이 되는지, 사용자당 하루 요청 수.
5. **MSIX 포장**: Godot .NET 결과물을 MSIX로 묶어 Store 제출 요건(전체 신뢰, 프로토콜)을 통과하는지. MSIX 안에서도 Shell COM과 투명 창이 똑같이 동작하는지.
6. **자원 사용**: §6-3 목표치 실측.
7. **창 지형**: 창 목록과 가림 계산을 1초·200ms 주기로 돌릴 때의 비용, 여러 모니터·DPI가 섞인 환경에서 좌표가 맞는지.

## 12. 첫 출시까지의 순서

1. 시험 제작(§11)
2. 혼자 놀기: 내 캐릭터가 작업표시줄·아이콘을 걷고 오르고 넘어짐, 전체 화면 숨김, 트레이. **[설계 결정] 혼자 놀기는 로그인 없이 된다.** Store에서 설치하자마자 내 캐릭터가 나타나고, 로그인은 친구를 초대하거나 초대를 받을 때 한다. 처음 쓰는 사람이 넘어야 할 문턱을 낮추기 위해서다.
3. 지형 확장: 열린 창 위 가장자리, 여러 모니터
4. 로그인, 방 만들기, 방 객체(DO) 접속으로 친구 캐릭터 보이기
5. 행동 동기화, 공 던지기, 말풍선, 채팅 창
6. 펫, 여러 방(한 번에 하나 켜기, 펫 알림), 빨리 숨기기 단축키
7. 초대 링크, 웹사이트, 카카오톡 공유
8. 물건과 일반 규칙(§6-9): 집기·던지기·쌓기·부서지기
9. 나의 WORLD: 구역·씨앗·자라기(혼자), WORLD 객체 저장
10. WORLD 방문: 방문자 권한, 하루 1번 되돌리기, 기본 자물쇠, 방명록·선물
11. Store 제출 → **시범 운영**(친구 몇 그룹)
12. 시범 반응 반영, 부하 시험
13. **SNS 마케팅과 함께 공개 출시**

**[설계 결정]** 꾸미기 판매(결제)는 첫 출시에 넣지 않는다. 먼저 친구 그룹이 계속 쓰는지 확인하고, 그다음 Microsoft Store 앱 내 구매로 붙인다. 캐릭터 꾸미기 데이터 구조(`profiles.avatar`)는 처음부터 둔다.

## 13. 사용자가 정할 열린 질문

1. **다음 게임 순서** — 시범 운영 반응을 보고 정한다. 자유도 원칙상 "게임"도 정해진 기능보다 물건과 규칙의 조합(§6-9)으로 만들 수 있는지 먼저 본다. 첫 출시 설계에는 영향이 없다.

해결된 질문(2026-11-22): 열린 창 지형(포함), 여러 방(한 번에 하나 + 펫 알림), 여러 모니터(내 모든 모니터), 캐릭터(코드로 그린 이족보행, 부위별 교체 구조), WORLD 저장(서버 + 내 PC 사본), 첫 출시 규모(시범 → SNS 공개 출시), WORLD 방문(주인이 꺼져 있어도 가능, 방문자 권한 거의 전부, 하루 1번 무료 되돌리기, 자물쇠·경비견 판매), 실시간 서버(Cloudflare DO).
